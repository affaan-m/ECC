# 编码风格

## 不可变性（关键）

始终创建新对象，绝不改变现有对象：

```
// 伪代码
WRONG:  modify(original, field, value) → 原地修改 original
CORRECT: update(original, field, value) → 返回包含更改的新副本
```

理由：不可变数据可以防止隐藏的副作用，使调试更容易，并支持安全的并发。

## 文件组织

多个小文件 > 少数大文件：

* 高内聚，低耦合
* **数代码行，不数总行数。** 与任何阈值比较之前，先排除纯注释行与空行。一个注释密集的文件不是大文件；把注释和代码按同一税率征税，只会让人先删解释——那与你想要的正好相反。
* **典型 ~200 代码行。400 代码行是"要写一句理由"的线，不是"到此为止"的线。**
* **一个类型不应同时持有多于两条独立生命周期**（Task / 订阅 / 定时器 / 观察者）。超过就说明它在协调而不只是持有状态——把协调器拆出去。这个信号比任何行数都更早、更准：缺陷聚集在多条独立生命周期的交织处，不在第 401 行。
* 从大型模块中提取实用工具
* 按功能/领域组织，而不是按类型组织

行数阈值是**烟雾报警器，不是消防规范**——它唯一的作用是让人去看一眼，价值来自看到了什么。**绝不能靠把代码挪到别的文件、或压缩注释来满足它**，那是规避指标而不是满足指标。要么按职责拆，要么不拆。

**全仓机械扫描，不许点名嫌疑人**——后者正是一条早已越线的约束能被每个查过的人报成"满足"的原因：

```bash
# 文件通配符与注释模式按语言调整。
find src tests -name '*.ext' | while read -r f; do
  n=$(grep -vcE '^[[:space:]]*(//|#|\*|$)' "$f"); [ "$n" -gt 400 ] && echo "$n $f"
done
```

## 错误处理

始终全面处理错误：

* 在每个层级明确处理错误
* 在面向用户的代码中提供用户友好的错误消息
* 在服务器端记录详细的错误上下文
* 绝不默默地忽略错误

## 输入验证

始终在系统边界处进行验证：

* 在处理前验证所有用户输入
* 在可用时使用基于模式的验证
* 快速失败并提供清晰的错误消息
* 绝不信任外部数据（API 响应、用户输入、文件内容）

## 代码质量检查清单

在标记工作完成之前：

* \[ ] 代码可读且命名良好
* \[ ] 函数短小（<50 行）
* \[ ] 没有类型持有多于两条独立生命周期（Task/订阅/观察者）
* \[ ] 文件聚焦（<400 **代码**行，不含注释；超过则要写一句理由）
* \[ ] 没有深度嵌套（>4 层）
* \[ ] 正确的错误处理
* \[ ] 没有硬编码的值（使用常量或配置）
* \[ ] 没有突变（使用不可变模式）
