# スキル品質証拠プレイブック

Candidate id: `evidence-backed-skill-amendment`

PR またはフォローアップが、スキル・エージェント・コマンド・ルールのガイダンスサーフェスの追加・書き直し・修正を提案する場合に、このプレイブックを使用してください。

## 受け入れパス

1. 変更したガイダンスサーフェスとソースファイルを明記する。
2. `docs/SKILL-DEVELOPMENT-GUIDE.md` から品質コントラクトを取得する。
3. 提案された変更を、`skills/*/SKILL.md` 配下の近隣の焦点を絞った例と比較する。
4. 変更を正当化する証拠のソースを記録する:
   - 観察されたスキル実行の失敗
   - ユーザーからのフィードバック
   - 繰り返されるレビューの検出結果
   - 参照セットのギャップ
   - 失敗した例またはリグレッションテスト
5. スコープを狭く保つ。1つのスキルは1つのドメイン・ワークフロー・再利用可能なパターンをカバーすること。
6. 検証できる場合にのみ、例を追加または更新する。
7. 関連するバリデーションゲートを実行する:
   - `node scripts/ci/validate-skills.js`
   - `node tests/lib/skill-improvement.test.js`
   - `node tests/lib/skill-evolution.test.js`
   - `npm run catalog:check`
   - 例に触れる場合は言語固有のコマンド（`npx tsc --noEmit`・`python -m py_compile`・`go build` など）
8. バリデーション出力・ソース帰属・ロールバックノートをメンテナーの PR 本文またはハンドオフに記録する。

## 拒否パス

観察された失敗の証拠・例・参照セットなしに、文章が「より良く聞こえる」という理由だけで曖昧なスキルの書き直しを昇格させてはならない。

焦点を絞ったスキルを重複させたり、アクティベーションの予測可能性を低下させたりする、複数ドメインを対象としたキャッチオール型スキルをマージしてはならない。

プライベートなオペレーターコンテキスト・シークレット・トークン・個人パス・顧客データ・未公開のリリースクレームをスキルにコピーしてはならない。

エバリュエーター実行から、パッケージマニフェスト・プラグインマニフェスト・カタログ・リリースノート・公開状態を更新してはならない。

## 最低限のバリデーション

- `node scripts/ci/validate-skills.js`
- カタログ/パッケージに公開されるスキルサーフェスが変更された場合は `npm run catalog:check`
- 修正動作が変更された場合は、スキルの改善またはスキルの進化に関する絞り込まれたリグレッションテスト
- 変更した例に対する言語固有のコンパイル/lint チェック
- `git diff --check`
- ドキュメントまたはプレイブックを変更した場合は Markdown lint

コントリビュートされたスキル素材のソース帰属を保持し、将来のメンテナー PR 向けにロールバックのガイダンスを含めること。
