# レイテンシクリティカルシステム

ユーザーがリアルタイムの挙動、ホットパス、ストリーミングの鮮度、または実行速度を重視する場合に、このスキルを使用する。HFTのようなインフラを含むが、このスキルはエンジニアリングに焦点を当てている。実際の取引や財務アドバイスを承認するものではない。

## メトリクスを分けて管理する

すべてを「速い」にまとめないこと。以下を追跡する：

- p50、p95、p99レイテンシ；
- スループット；
- 鮮度の経過時間；
- キューの深さ；
- キャッシュのヒット率；
- プロバイダー/APIの応答時間；
- ブラウザのレンダリング時間；
- 負荷下での正確性；
- 障害とリトライの挙動。

## ホットパスをマッピングする

ユーザー/イベントから最終的な可視状態までのパスを記載する：

```text
source event -> provider API -> ingest worker -> queue -> cache -> edge route
-> client stream -> browser render -> user-visible state
```

その後、各セグメントを個別に計測する。

## 最適化の順序

1. 不要なラウンドトリップを排除する。
2. 鮮度メタデータを持つ安定した読み取りをキャッシュする。
3. 小さな呼び出しと書き込みをバッチ処理する。
4. 計算をデータまたはユーザーの近くに移動させる。
5. ホットパスとコールドパスを分割する。
6. キューが際限なく成長する前にバックプレッシャーを適用する。
7. 鮮度やユーザー体験を向上させる場合にのみストリーミングを使用する。
8. 古いデータ、劣化したプロバイダー、不正なキャッシュ状態に対するカナリアを追加する。

## 検証

デプロイされたサーフェスが存在する場合は、ライブリードバックを使用する：

- HTTPタイミングとレスポンスヘッダー；
- プロバイダーの鮮度タイムスタンプ；
- キューまたはジョブの状態；
- エッジ/キャッシュの状態；
- 実際のUIの鮮度を確認するためのブラウザ検証；
- リトライと劣化モードに関するログ。

マーケットデータまたは実行に近いパスについては、パスを準備完了と呼ぶ前に、オーダーブックの経過時間、VWAP の前提、プロバイダーのステータス、キルスイッチの挙動も検証すること。

## ガードレール

- 必要な検証を省略してレイテンシを最適化しないこと。
- 高速なキャッシュヒットの背後に古いデータを隠さないこと。
- クライアントのラベルだけで計測なしにミリ秒の挙動を主張しないこと。
- 明示的な承認ゲートなしに、実際の注文、破壊的なマイグレーション、または顧客影響のあるデプロイを実行しないこと。
- シークレットとプライベートなペイロードをログとベンチマーク成果物から除外すること。
