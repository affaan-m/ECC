# recsys-pipeline-architect

コンポーザブルなレコメンデーション・ランキング・フィードパイプラインを構築するためのスペック＆スキャフォールドスキル。xAI がオープンソース化した [For You アルゴリズム](https://github.com/xai-org/x-algorithm)（Apache 2.0）で広まった **6 段階パターン** — Source → Hydrator → Filter → Scorer → Selector → SideEffect — を実装する。このスキルは当該パターンの独立した再実装（MIT）であり、元のコードは一切使用していない。

アップストリーム: <https://github.com/mturac/recsys-pipeline-architect>

## 使用するタイミング

- 「ユーザー/コンテキストに対してトップ K アイテムを選ぶ」システムをユーザーが構築したい場合
- 「X をどのようにランキングすればよいか」とユーザーが尋ねる、またはフィード/パーソナライゼーションの問題を説明している場合
- スコアリング関数があり、その周囲のパイプライン配管が必要な場合
- 単一の関連スコアからチューナブルな重みを持つマルチアクション予測に移行したい場合
- LLM/ML スコアラーをラップしており、フィルタ・ハイドレータ・サイドエフェクト・実行可能なスキャフォールドをスタック（TypeScript / Go / Python）で必要としている場合
- トリガーワード: 「レコメンデーションシステム」「フィードアルゴリズム」「ランキングパイプライン」「For You フィード」「候補パイプライン」「コンテンツレコメンダー」「recsys のパイプラインアーキテクチャ」「RAG 検索リランカー」

## 使用しないタイミング

- モデルアーキテクチャの作業（トランスフォーマー設計、ツータワー検索、埋め込みトレーニング）— このスキルはモデルそのものではなく、モデルの *周辺* の配管を扱う
- 純粋な ML トレーニングパイプライン — スコアリング関数はユーザーの責任範囲
- デプロイ済みパイプラインの運用（モニタリング、オートスケーリング）— スコープ外

## 6 段階フレームワーク

| # | ステージ | 役割 | 並列実行? |
|---|---|---|---|
| 1 | **Source** | 1 つ以上のオリジンから候補を取得する | あり — 複数ソースが並列実行 |
| 2 | **Hydrator** | フィルタリングとスコアリングに必要なメタデータで各候補をエンリッチする | あり — 独立したハイドレータが並列実行 |
| 3 | **Filter** | 表示すべきでない候補を除去する（ブロック済み、期限切れ、重複、対象外） | 逐次 — 各フィルタはより少ないアイテムを処理する |
| 4 | **Scorer** | 残った各候補に 1 つ以上のスコアを付与する | 逐次 — 後のスコアラーは前のスコアを参照できる |
| 5 | **Selector** | 最終スコアでソートしてトップ K を返す | 単一操作 |
| 6 | **SideEffect** | 配信済み ID のキャッシュ、インプレッションのログ記録、イベント送信、カウンタ更新 | 非同期 — レスポンスをブロックしてはならない |

### この順序である理由

- ハイドレーション前にソース: エンリッチメントのコストを払う前に候補が何であるかを把握する
- フィルタリング前にハイドレーション: 多くのフィルタはソースが提供しなかったメタデータを必要とする
- スコアリング前にフィルタリング: スコアリングは高コストなステージ。対象外を先に除去する
- 単一スコアラーではなくスコアラーチェーン: 実際のシステムは ML スコアリング + 多様性リランキング + ビジネスルールを組み合わせる
- スコアリング後にセレクタ: スコアリングを決定論的かつキャッシュ可能に保つ
- サイドエフェクトは最後で非同期: サイドエフェクトはユーザーレスポンスをブロックしてはならない

## 呼び出し時のワークフロー

以下の 8 つのステップをユーザーとともに進める:

1. **ユースケースの明確化**（1 ラウンド、3 つの質問）: ランキング対象のアイテム、入力コンテキスト、言語/ランタイムは何か?
2. **候補ソースの特定**: 通常はインネットワーク（フォロー/所有/購読済み）+ アウトオブネットワーク（ML 検索 / トレンド / 類似コンテンツ）
3. **必要なハイドレーションの列挙**: 各フィルタとスコアラーが必要とする、ソースが提供しなかったデータを特定する
4. **フィルタの列挙**: 重複、自己投稿、年齢、ブロック/ミュート、配信済み、対象資格。順序が重要 — 安価なものを先に。
5. **スコアラーチェーンの設計**: プライマリ（ML）→ コンバイナー（重み付きマルチアクション）→ 多様性 → ビジネスルール
6. **セレクタ**: 最終スコアの降順でソートし、トップ K を取得する（インネットワーク/アウトオブネットワークの層別ミックスも可）
7. **サイドエフェクト**: 配信済み ID のキャッシュ、インプレッションイベントの送信、カウンタ更新、分析ログ — すべてファイヤーアンドフォーゲット
8. **ユーザーのスタックでスキャフォールドを生成する**

## 表面化すべきトレードオフ（暗黙のデフォルトにしない）

### 1. 単一スコアとマルチアクション予測

- **単一スコア**: 関連性を予測するモデルを 1 つ訓練する。挙動を変更するには再訓練が必要。
- **マルチアクション**: 多くのアクション（読む、いいね、シェア、スキップ、報告など）に対して `P(action)` を予測し、配信時に重みで組み合わせる。挙動を変更するには重みを変えるだけでよく、再訓練は不要。

X の For You システムはポジティブとネガティブの両方の重みを持つマルチアクションを使用する。頻繁にチューニングが必要な場合はマルチアクションを推奨する。

### 2. スコアリングにおける候補の独立性

- **独立型**: 各候補を独立してスコアリングする。決定論的でキャッシュ可能。
- **結合型**: スコアリング中に候補同士がアテンションを行う（例: バッチに対するトランスフォーマー）。より表現力が高いが、バッチをまたいで非決定論的になる。

独立型をデフォルトとする。結合型は特定の理由がある場合のみ（例: 明示的なバッチ対応の多様性）。

### 3. オンラインとオフライン

- **リクエスト時（オンライン）**: リクエストごとにパイプラインが実行される。レイテンシ予算: 100〜300ms。デフォルト。
- **事前計算（オフラインバッチ）**: パイプラインが定期的に実行され結果がキャッシュされる。低レイテンシだが鮮度は低い。
- **ハイブリッド**: 候補検索はオフライン、ランキングはオンライン。

## 必守ルール

1. **ベンチマーク数値を作り上げない。** 「どれくらい速いか?」→「ワークロードによる。自分で計測してほしい。」
2. **帰属表示の規律。** このパターンを参照する際は「xAI がオープンソース化した For You アルゴリズムで広まった」/ `github.com/xai-org/x-algorithm`（Apache 2.0）と帰属を明示する。
3. **商標の不使用。** ユーザーの成果物を「X ライク」と命名したり「For You」ブランドを使用したりしない。パターンは自由に使えるが、ブランドは異なる。推奨する命名: 「候補パイプライン」「フィードパイプライン」「ランキングパイプライン」「recsys パイプライン」。
4. **トレードオフを表面化する。** マルチアクション対単一、独立対結合、オンライン対オフライン — 暗黙のデフォルトにしない。
5. **生成したスキャフォールドは動作すること。** 擬似コードをコードとして提出しない。
6. **フィルタの順序が重要。** 安価なものを先に、ユニバーサルなものをユーザー固有のものより先に。
7. **サイドエフェクトはブロックしない。** ファイヤーアンドフォーゲットパターンでラップする（ゴルーチン / await なし Promise / asyncio タスク）。

## アンチパターン

- フィルタリング前にスコアリングを行う（どうせ除去される候補のコンピュートを無駄にする）
- 同期的なサイドエフェクト（キャッシュ書き込みやインプレッション送信がレスポンスをブロックする）
- 製品が複数の目的（エンゲージメント vs 安全性 vs 多様性 vs 広告）のチューニングを必要とするのに単一の「関連性」スコアを使用する
- 結合スコアリングをデフォルトにする（非決定論的でキャッシュが難しく、リランキングステージと組み合わせにくい）
- 「説明のため」として擬似コードを生成する — スキャフォールドは実際に動作しなければならない
